## 一、可改进的算法点（按优先级）

### P1-1 账本截断是「直接覆盖」，崩在中间丢整份历史

- **位置**：`bridge/workbuddy-bridge.mjs:1696-1700`
- **现状**：超过 `MAX_USAGE_LINES = 2000` 时 `usageLines = slice(-1000)` 然后
  `writeFileSync(file, text)` —— **非原子、无备份**
- **问题**：截断那一刻进程被杀 / 断电 → 文件半写 → 本地用量历史全丢
  （内存镜像也与文件不一致）。触发频率约每 1000 次请求一次。
- **影响**：丢的是**用户自己的历史数据**，且项目里没有第二份副本 —— **不可逆**。
- **现有覆盖**：无（`MAX_USAGE_LINES` 在测试里出现 0 次，截断路径从未被执行过）。
- **为什么排第一**：发生概率不高（要正好崩在那一次写），但「影响不可逆 + 修法成熟 +
  改动极小」三条叠起来，性价比最高。而且截断逻辑本身**从没被执行过**，
  写错了（比如 slice 方向反了）也没人知道。
- **建议**：临时文件 + `renameSync`（同目录内 rename 在 Windows 上也是原子的），
  与项目既有标准对齐 —— `lib/dsh.mjs:268` 写 dsh 配置时是**先 `copyFileSync` 备份再写**，
  账本这条比它更该保守；顺带补一条 >2000 行的用例。

### P2-1 凭据刷新没有单飞

- **位置**：`bridge/workbuddy-bridge.mjs:1049`（主路径）与 `:1083`（重试路径）调用
  `refreshAuth()`（定义在 `:639`）
- **现状**：每个请求各自判断「令牌快过期了」然后调 `refreshAuth`；并发之间**没有去重**
  （`refreshAuth` 里只有失败冷却 `lastRefreshFailedAt`）。
  **限流默认是关的**（`:994`：两个阈值都为 0 时直接返回），所以并发请求真的并行 ——
  没有别的东西替它串行化。
- **问题**：令牌过期瞬间到达的 N 个并发请求，各自打一次上游刷新。而响应里可能带
  **轮换后的 refreshToken**（实现里 `refresh: body.data.refreshToken || auth.refresh`
  说明轮换是预期行为）—— 后到的请求拿着已作废的旧 refreshToken 必然失败，
  于是写 `lastRefreshFailedAt`，**接下来 15 秒（`REFRESH_COOLDOWN_MS`）所有刷新被冷却挡住**。
- **影响**（分两档，别混着说）：
  - **确定**：每次过期多打 N-1 次刷新，日志里多几条 `refresh failed`；
  - **推测**：若上游对 refreshToken 做了「重复使用即吊销」这类检测，
    并发复用同一个旧令牌可能**吊销整个会话 → 用户被迫重新登录**。
    这条没有验证过（取决于上游行为），但代价足够大，值得按单飞处理掉。
  - **曾经以为、实测不成立**：不会造成「连续 401」。`readStoredAuth()`（`:604`）
    优先返回内存里刷新过的令牌，只要**有一次**刷新成功，后续请求就都用新令牌了。
- **现有覆盖**：只有**单次**刷新失败的用例（`桥：刷新失败时不得把响应体写进日志`）。
  并发刷新**没有用例**（并发用例走的是限流路径，令牌有效）。
- **建议**：`refreshAuth` 包成单飞（模块级 `let refreshPromise`，同飞共享同一个 promise）；
  并把「refreshToken 被明确拒绝」与「网络/超时」分开，后者不该进冷却。

### P2-2 流式转发没有背压处理

- **位置**：`bridge/workbuddy-bridge.mjs:1461` 的 `write()`
  （`res.write(...)` 不看返回值、不 `await` `drain`；全文件 `drain` 出现 0 次）
- **现状**：上游读多快就往 `res` 写多快
- **问题**：客户端**读得慢或干脆不读但也不断开**时，Node 把待发数据堆在内存里
  （`res.write` 返回 `false` 表示已超水位，这里完全忽略）。客户端的
  `res.on('close')` 只覆盖「断开」，覆盖不了「停顿」。
- **影响**：内存随「停顿时长 × 上游速度」增长。**有界**（单次上游响应有限），
  所以不是致命问题；但一个卡住的客户端 + 长回答是能看出来的。
- **现有覆盖**：无（用例里有「客户端断开」，没有「客户端停顿」）。
- **建议**：`write()` 里 `if (!res.write(chunk)) await once(res, 'drain')`，
  并给一个总等待上限（超时就 abort，记一条失败）。

### P3-1 「今天」有两个实现，一个本地一个 UTC

- **位置**：`dashboard/public/index.html:1885` 的 `today()`
  （`new Date().toISOString().slice(0, 10)`）vs `:2186` 的 `localDateStr()`
- **现状**：`localDateStr()` 是本地日期，注释写明「与桥的 `localDay` 同规则」；
  而 `today()` 用 `toISOString()`，那是 **UTC 日期**，两者在 UTC+8 的 00:00–08:00
  会差一天
- **问题**：`today()` 只用在 **CSV 文件名**（`:3923 / :3955 / :3983`）——
  凌晨导出的文件会叫「昨天」
- **影响**：小（只是文件名），但属于「同一个概念两套实现」，迟早有人拿它去算别的
- **现有覆盖**：无（文件名不参与断言）
- **建议**：删掉 `today()`，三处改用 `localDateStr()`

### P3-2 `persistRefreshed()` 名字与行为相反，且调用时机反直觉

- **位置**：`bridge/workbuddy-bridge.mjs:687`（调用）/ `:686`（定义）
- **现状**：函数名叫 `persistRefreshed`，实现只打一行
  `log('write-back skipped: ...')`，是个**空操作**；而且它在 `memoryAuth = {...}`
  **之前**被调用
- **问题**：名字承诺「持久化」，行为是「明确不持久化」——未来读代码的人极可能
  以为令牌已经落盘。调用顺序也让人以为「先落盘再更新内存」
- **影响**：维护性；这条「绝不回写」是本项目的硬约束，代码不该长得像在回写
- **建议**：改名 `logWriteBackSkipped()` 并移到 `memoryAuth` 赋值之后（或直接内联那一行日志）

### P3-3 流式行缓冲无上限

- **位置**：`bridge/workbuddy-bridge.mjs:1510` 附近的 `buffer += decoder.decode(...)`
- **现状**：按 `\n` 切分，切不出换行时全部留在 `buffer`
- **问题**：上游若持续不发换行，`buffer` 无界增长
- **影响**：概率极低（上游是自家网关），但代价是进程内存
- **现有覆盖**：无
- **建议**：`buffer` 超过阈值（如 1MB）就 abort 并记一条失败，别静默增长

## 二、遗漏的覆盖范围（按影响排序）

| 场景 / 边界 | 现状 | 潜在影响 |
|---|---|---|
| **账本截断路径**（>2000 行，P1-1） | 无用例，代码从未被执行过 | 截断逻辑写错（如 slice 方向反）没人发现；崩溃丢历史 |
| **并发刷新**（P2-1） | 只有单次失败用例 | 多打 N-1 次上游刷新；推测最坏是会话被吊销 |
| **客户端停顿不断开的背压**（P2-2） | 只覆盖了「断开」 | 内存增长（有界） |
| **跨天 / 跨时区的分桶边界** | `localDay()`（桥 `:1780`）按本地日期切；**没有跨天用例** | 分桶错位是「数字看着不对」这类最难查的问题 |

| 流中途断开记失败 | 有用例 ✓ | 覆盖到了 |
| 客户端断开时在途请求的登记/释放 | 有用例（三条路径）✓ | 覆盖到了 |

## 三、优先级与理由

排序用的不是「哪个更严重」，而是**影响 × 不可逆性 × 修法成熟度**：

1. **P1-1 账本截断原子化** —— 概率不高（要正好崩在那一次写），但**丢的是不可再生的
   用户数据**、修法成熟（temp + rename）、改动只有几行，而且顺带能把一条
   **从没被执行过**的代码路径纳入测试。性价比最高。
2. **P2-1 刷新单飞** —— 「确定的影响」只是浪费，但「推测的影响」是用户被迫重新登录；
   修法小（一个模块级 promise），且能把「明确被拒」与「网络失败」的冷却语义分开。
3. **P2-2 背压** —— 影响有界、可观测，改动也小；排在数据问题之后。
4. **P3-1 / 3-2 / 3-3** —— 都是「现在不出事、以后会」：两个 `today()` 实现、
   名字骗人的空操作、无上限缓冲。可以合批做，一次提交。
5. **补用例**（账本截断、并发刷新、跨天分桶）—— 建议**与对应修复同批**，
   先写会红的用例再改实现（项目既有纪律：先红后绿）。

**不建议现在动的**：i18n 引擎（见第五节，实测不是热点）、
流式解析的行缓冲与工具块索引（写得很细，动了风险大于收益）。

## 四、写得好、不需要动的地方

避免只报坏消息，这几块是读完确认**扎实**的：

- **账本镜像的失效判据**（`:1638` `syncUsageMirror`）：从「只比字节数」演进到
  「字节数 + mtime 指纹」，注释里把两次踩坑的序列（外部删除→重建→永远读 0）都记了 ——
  这是本项目注释质量的一个缩影。
- **刷新失败的日志脱敏**（`:650`）：明确因为「非 2xx 的响应体也可能带 accessToken」
  而只记协议层 code/msg。这条很容易被后人"顺手"改回打印全文。
- **流式解析**：行缓冲 + `TextDecoder({stream:true})` 多字节安全 + 工具块按
  `tc.index` 分槽并在新块前关闭旧块（Anthropic 的 block 索引必须连续）。
- **控制台的单飞与可见性感知轮询**（`index.html:2062` `singleFlight` + 轮询调度）：
  手动刷新与轮询共用同一把锁，慢响应不会叠并发。
- **空态处理**：趋势图「窗口内全 0 → 说清楚，不画空轴」；占比条 `Math.max(..., 0.0001)`
  防除零并给 2% 下限让极小值可见。

## 五、两条被实测改判的怀疑（方法说明）

**1. i18n 规则引擎没有缓存 —— 实测不是问题。**
每个字符串线性扫 174 条正则，看着像 `O(元素数 × 规则数)` 的热点。
实测 `applyI18n()` 一次完整遍历 **0.5–1.7ms**，单条翻译 2000 次平均 < 0.001ms。
表命中是 O(1)，只有未命中的串才走规则表，而串都很短。**不需要优化**
（记在这里，免得下次再怀疑一遍）。

**2. 刷新并发这条，我先高估、又差点低估。**
第一版写成「P1：过期瞬间连续 401」—— 查 `readStoredAuth():604` 才发现它**优先返回
内存里刷新过的令牌**，只要有一次刷新成功，后续请求就都用新令牌了，**不会**连续 401。
于是想降级，理由是「限流会串行化」—— 再看 `acquireRateSlot():994`，限流
**默认关闭**（两个阈值都为 0 时直接返回），根本没串行化。
最后落点是：**确定的**影响是多打 N-1 次刷新，**推测的**影响是会话可能被吊销，
按 P2 处理。两次判断都是靠读代码定的，两次都被下一行代码推翻 —— 所以每条结论
都标了「确定 / 推测」，不混着写。
